## 作業内容

### 1. カレンダー（日付の入力）

今は `<input type="date">` で、ブラウザ・OS 標準のピッカーが出る（`globals.scss` の `color-scheme: dark` で暗くはなるが、ページの色・角丸・文字とそろわない）。

#### 方針: ライブラリ `react-day-picker` を使う（推奨）

| 観点 | 独自 UI | `react-day-picker`（MIT） |
| --- | --- | --- |
| 見た目の自由度 | 完全に自由 | CSS 変数とクラス名の上書きで、ほぼ自由に変えられる（構造を持つだけで見た目は持たない作り） |
| キーボード操作・読み上げ | 矢印キーでの日付移動、月の送り、`aria-*`、フォーカスの管理を自前で作り、テストする必要がある | 組み込み済み（WAI-ARIA の grid に沿う） |
| 日付処理 | date-fns で自前で組む | date-fns を土台にしている（このプロジェクトも date-fns 4 を使っているので相性がよい）。`date-fns/locale` の `ja` で日本語にできる |
| 祝日の表示 | 自前 | `modifiers` に `@holiday-jp/holiday_jp` の判定を渡すだけで、祝日・土日に色を付けられる |
| 依存が増える | なし | 1 つ（依存先は `date-fns` と `@date-fns/tz` だけ） |

- **推奨は `react-day-picker`**。見た目は自由に変えられ、カレンダーで手間のかかる部分（キーボード操作・アクセシビリティ・月の送り）を自前で作らずに済む。身内向けの小さなサイトで、カレンダーのためにテストの多い自前の部品を抱えるのは割に合わない
- 2026-10-30 時点の最新は v10.0.2（MIT、peerDependencies は `react >=16.8`）。**v10 の API は記憶に頼らず、`node_modules/react-day-picker` の型定義と README を読んでから使う**（v8 → v9 で API が大きく変わっており、v10 も変わっている可能性がある）
- 追加: `pnpm add react-day-picker`。`package.json` と `pnpm-lock.yaml` の差分を確認する
- もし型定義を読んで、React 19 で動かない・見た目を変えられないなど問題が見つかったら、独自 UI に切り替える前にユーザーに相談する

#### 作るもの

- `components/DateField/`（`DateField.tsx` / `DateField.module.scss` / `useDateField.ts` / `index.ts`）
  - 見た目は今の入力欄と同じ枠のボタン。「2026/10/30（金）」のように曜日付きで表示し、押すとすぐ下にカレンダーを出す
  - props: `id` / `value: TDateString` / `onChange(value: TDateString)` / `isInvalid` / `label`（読み上げ用）
  - 値は `"YYYY-MM-DD"` の文字列のまま受け渡す（`Date` への変換は `useDateField` の中だけで行う。データ設計のルールのため）。変換は `gantt.utils.ts` に既にある関数を使い、なければそこに足してテストする
  - カレンダーの開閉: もう一度ボタンを押す・日付を選ぶ・Esc・外側をクリックで閉じる。**Esc はカレンダーだけを閉じ、サイドパネルは閉じない**（`useProjectSidePanel` の Esc の処理より先に止める必要がある。今の Esc の扱いを読んでから決める）
  - 開いたときは選んでいる日付の月を出し、その日にフォーカスを置く
  - 土日・祝日・今日の色はタイムラインの色（下の 5 章）と同じトークンを使う
  - パネルの下端で切れないよう、カレンダーはパネルの中に収まる位置に出す（開始日・終了日は横並びなので、終了日のカレンダーは右寄せで出す）
- `ProjectSidePanel` の開始日・終了日の `<input type="date">` を `DateField` に置き換える。検証（`projectForm.utils.ts`）は変えない

#### 範囲を 1 つのカレンダーで選ぶ案（今回はやらない）

`react-day-picker` は開始日と終了日を 1 つのカレンダーでまとめて選べる（`mode="range"`）。操作が変わるので今回は入れず、2 つの欄のままにする。使ってみて欲しくなったら別に検討する。

### 2. 「案件を追加」ボタンのクリック範囲

- 今は `.addProjectButton` が文字の幅（高さ 24px）しかなく、行の大部分を押しても反応しない
- 案件の行の `.projectButton`（`MemberListProjectRow.module.scss`）と同じく、ボタンを行いっぱい（`flex: 1` / `height: 100%`）に広げる。ホバーの色は行全体に付ける
- 文字の左端の位置は今の案件名とそろえる（行の左の余白はボタンの中の `padding` で取る）

### 3. 文字の大きさ（最小 16px）

- 方針: **トークンの値を変える**。`_tokens.scss` の `$font-size-xs` / `$font-size-sm` / `$font-size-md` を 16px 以上にし、それより大きい見出し用の段も上げる。各コンポーネントの `font-size` の指定は、基本的にトークン名のまま変えない
  - 案: `xs: 16px` / `sm: 16px` / `md: 16px` / `lg: 18px`。ただし 3 段が同じ値になるので、段の名前と使い分けを整理する（例: `$font-size-base: 16px` / `$font-size-lg: 18px` / `$font-size-xl: 20px` にまとめ、`xs`・`sm` の参照を置き換える）。どちらにするかは実装の最初に差分の大きさを見て決め、報告に理由を書く
  - 大きさの差がなくなる分、補足の文字（件数・ラベルなど）は色（`$color-text-muted`）と太さで区別する
- 例外: 文字ではなく記号として使っているもの（開閉の三角 `▼` の 9px、つかみの `⋮⋮`）は 16px にしない。アイコンとして扱い、見た目の大きさで決める
- 文字が大きくなって収まらなくなる箇所を確認し、必要なら定数（`gantt.constants.ts`）とトークンを調整する
  - 日の列の幅（`DAY_COLUMN_WIDTH = 32`）: 「30」が 16px で収まるか。今日の丸いバッジも含めて確認する
  - 日付ヘッダーの月の行（`DATE_HEADER_MONTH_ROW_HEIGHT = 24`）・日の行（28）
  - 帯の中の案件名（帯の高さは行 36px − 上下 6px ずつ = 24px）と、ドラッグ中に出す期間の表示
  - 左のリストの幅（`MEMBER_LIST_WIDTH = 240`）、担当者の件数のバッジ、ヘッダーのボタン（480px 以下の狭い画面も）
  - サイドパネル・担当者の管理ダイアログ・確認ダイアログのボタンとラベル
- 行の高さや列の幅を変えたときは、帯の位置の計算（`gantt.utils.ts`）のテストが定数を前提にしていないか確認する

### 4. 「今日」のアニメーションをなくす

- `useTimelineScroll` の `scrollToPosition` に、なめらかにするかどうかの引数（`behavior: "smooth" | "instant"`）を足す
  - `scrollToToday` は `"instant"`、`scrollBackward` / `scrollForward`（月の移動）は今のまま `"smooth"`
  - 瞬間移動では途中で範囲の拡張が起きる心配がないが、目的地が左端に近いときに先に範囲を広げる今の処理（`while` の部分）はそのまま通す（広げないと目的地まで動けないため）
- 起動直後の初期位置（`attachScroller`）は今も瞬間移動なので変えない

### 5. 土日祝の色

- 今は土日の背景が白の 2.5%、祝日が赤の 7% でほぼ見分けられない。日付ヘッダーの文字も土日は灰色で目立たない
- 日本のカレンダーの慣習に合わせ、**土曜は青、日曜と祝日は赤**の系統にする（ユーザーと見た目を確認しながら決める）
  - トークン: `$color-saturday`（背景）/ `$color-saturday-text`、`$color-holiday`（日曜・祝日の背景）/ `$color-holiday-text` を見直す。背景の濃さは 8〜12% 程度から目で見て調整し、帯の色（特に青・赤のプリセット）と見分けがつくかも確かめる
  - 日付ヘッダーの数字にも同じ系統の文字色を付ける
- 土曜と日曜を分けるため、`IDayColumn` に曜日の情報を足す（例: `isWeekend` を `dayKind: "weekday" | "saturday" | "sunday"` に置き換える、または `isSaturday` を足す）。どちらにするかは参照箇所（`useTimelineGrid` / `useTimelineDateHeader` / テスト）の差分が小さい方を選ぶ。`gantt.utils.test.ts` を更新する
- 祝日が土日と重なったときは今と同じく祝日の色を優先する

### 6. 月の区切り

- 今は月が変わる位置に特別な線がない（日の列の 7% の線と同じ）
- 各月の 1 日の列の左に、はっきりした線（例: 2px、`$color-border-hover` 程度の明るさ。新しいトークン `$color-month-divider`）を引く
  - タイムラインの列（`TimelineGrid`）と、日付ヘッダーの日の行・月の行の両方で同じ位置に引き、上から下まで 1 本につながって見えるようにする
  - 1 日かどうかの判定は `IDayColumn` に `isMonthStart` を足すか、フックで `date` の日の部分から求める（5 章で `IDayColumn` を触るので、足す方を推奨）
  - 線の太さで列の幅がずれないよう、`border` ではなく `box-shadow: inset` か疑似要素で引く（帯の位置の計算は列の幅が一定である前提のため）
- 月の行の月の名前（「2026年10月」）は、スクロールしても各区間の左端に見えるようにするかを確認する（今の動きを変える場合は報告する）

### 7. サイドパネル下部のボタンの配置

今は下部に「完了にする（1 行いっぱい）」→「削除・キャンセル・保存」の 2 段になっている。「完了にする」は保存と同じくフォームを保存してパネルを閉じるが、意味は「案件の状態を変える」操作で、保存・キャンセル・削除とは性質が違う。いちばん押されやすい位置（保存の真上の幅いっぱいのボタン）にあるのも、誤って押しやすい。

#### 推奨案: 「状態」の欄をフォームの最上部に作り、そこへ移す

```
┌ 案件を編集 ─────────── ✕ ┐
│ 状態   ● 未完了   [✓ 完了にする] │  ← 完了済みなら「✓ 完了済み（10/30）  [未完了に戻す]」
│ 担当者 [         ▼]          │
│ 案件名 [                ]     │
│ 開始日 [ 2026/10/30（金）] 終了日 [...] │
│ 帯の色  ● ● ● ● ● ●          │
│ メモ   [                ]     │
├──────────────────────────────┤
│ 削除                キャンセル  保存 │
└──────────────────────────────┘
```

- 下部は「削除（左・赤の文字）／キャンセル・保存（右）」の 1 段に戻す。よく見る並び（破壊的な操作を主ボタンから離す）で、迷いが少ない
- 見出しの横にある「完了済み（10/30）」の札は、状態の欄に移す（同じ情報を 2 か所に出さない）
- 「完了にする」の動き（フォームの内容と一緒に保存して閉じる、検証で失敗したら完了にしない）はフェーズ 10 のまま変えない
- 追加のとき（`isEditing` が false）は状態の欄を出さない
- 下部のボタンの段はパネルの下に固定し、フォームが長くなってもスクロールせずに押せるようにする（今は `margin-top: auto` で下に寄せているだけなので、項目が増えると押し出される）

#### ほかの案（採らなかった理由）

- 見出しの右（✕ の左）に置く: 360px の幅に見出し・札・ボタン・✕ が並び窮屈。完了済みのときに「未完了に戻す」が長い
- 下部のまま「削除」の隣に小さく置く: 削除と同じ「状態を変える」まとまりにはなるが、下部に 4 つ並ぶと狭く、フェーズ 10 で折り返して 2 段にした問題に戻る

実装の前に、この配置でよいかをユーザーに確認する（見た目の好みが分かれるため）。

### 8. チャートの何もないところのクリックでサイドパネルを閉じる

- サイドパネルを開いているとき、タイムラインの何もない場所（帯のない行・担当者行・日付ヘッダー・左のリストの空いたところ）をクリックしたら、パネルを閉じる
- 閉じないもの
  - 帯（別の案件の帯なら、今と同じくその案件に切り替える）、帯の伸縮のつかみ
  - 左のリストのボタン類（案件名・「案件を追加」・担当者の開閉・担当者を管理・並び替えのつかみ）
  - ヘッダー（月の移動・今日・完了済みの切り替え）。パネルを開いたまま押せるようにした経緯（フェーズ 10）があるため
- 実装の方針: スクロール領域（`GanttChart` の `.scroller`）に `onClick` を 1 つ付け、クリックした要素が操作できる要素（`button` / 帯 など）の中なら何もしない。判定は `closest()` で行い、帯には判定用の `data-*` 属性を付ける。判定と閉じる処理は `useGanttChart`（または `useSidePanel`）に置き、tsx には結線だけを書く
  - 帯にそれぞれ `stopPropagation` を足す方法は、帯以外のボタンにも同じ対処が要り漏れやすいので採らない
- 注意（実装時にブラウザで確かめる）
  - 帯をドラッグして何もない場所で離したとき・左のリストで並び替えて離したときに、`click` がスクロール領域に届いて閉じてしまわないか（ポインターキャプチャ中の `click` の宛先）。閉じてしまうなら、ドラッグした直後の `click` を無視する
  - トラックパッドでの横スクロールでは閉じない
  - 入力途中でも確認せずに閉じる（Esc・✕ と同じ扱い。2026-10-30 にユーザーの確認済み）
