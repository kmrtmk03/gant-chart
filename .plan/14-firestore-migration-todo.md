## 1. 同時編集による上書き（issue #24）

### 現状

- 別のタブ（将来は別のユーザー）の更新は、画面に反映されない。`storage` イベントなどの購読はない
- 案件のサイドパネルは、開いた時点の全項目を保存する（`useProjectForm` が初期値を固定し、`useGanttPage.handleSaveProject` が全入力を `updateProject` に渡す）
- repository は現在値を読み直すが、渡された古いフィールドで置き換える。そのため、別タブで変えた項目を古い値で上書きする

### 再現手順

1. 同じ案件をタブ A と B で開く
2. B で案件名を変更して保存する
3. A でメモだけ変更して保存する
4. A の古い案件名も送信され、B の変更が失われる

### 移行時にやること

- `updatedAt` の照合による**競合検知**を設計する。保存時に「編集を始めたときの `updatedAt`」と現在の値を比べ、食い違えば上書きせずユーザーに知らせる
  - `IGanttRepository` の API 変更を伴う（`updateProject` / `updateMember` に、編集開始時の `updatedAt` を渡す引数が要る）
  - Firestore ではトランザクションか、`updatedAt` を条件にした書き込みで実装する
- 別ユーザー・別タブの更新を検知する方法（Firestore のリアルタイム購読か、再取得か）を決める
- 競合したときの編集中の下書きの扱い（捨てる・残して再編集させる）を決める
- 担当者の削除時に表示する「配下の案件 N 件」も、古い一覧に基づいている。削除時に最新の件数で確かめる
- 並び替え（`reorderProjects` / `reorderMembers`）は全 id を渡す契約で、別タブで増減があるとエラーになる。同時編集があっても意味が通る契約か見直す

### 先に入れられる暫定策（今はやらない）

フォームの初期値との差分だけを `updateProject` に送る。`TProjectUpdate` と repository は部分更新に対応済みで、別タブで変えた**別の項目**は上書きされなくなる。同じ項目を両方で変えたときは後勝ちのまま。

## 2. 移行時の前提（既存の方針の再掲）

- アクセスは Route Handler + Firebase Admin SDK でサーバー側からだけ行う。Firebase の設定値やサービスアカウント情報に `NEXT_PUBLIC_` を付けず、クライアントのコードに含めない
- Firestore の Security Rules はクライアントからのアクセスをすべて拒否にする
- コンポーネントは `IGanttRepository` だけを経由する（`ApiRepository` を足して差し替える）
- localStorage の保存データ（`gantt:*`）を Firestore へ取り込む手順が要るか、オーナーに確認する（身内利用のため、サンプルデータの入れ直しで足りる可能性がある）
